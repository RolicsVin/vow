# О проекте

**«Обет»** — визуальная новелла о человеке, решившем подняться на самую высокую гору и сразить богов. Игра разрабатывается по книге «Обет» О. Р. Михайловича.

## Архитектура проекта

Проект построен на модульной архитектуре. Центральное ядро отвечает за общие механизмы и координацию, а отдельные игровые модули инкапсулируют собственные данные и логику. Взаимодействие между ними организовано через Autoload-синглтоны Godot.

### Общая схема

```text
project.godot
│
├── PythonBridge       # Связь GDScript с Python
├── Core               # Центральное ядро и общие инструменты
├── Data               # Общие данные проекта
├── GminiGame          # Модуль мини-игр
├── GVisualNovel       # Модуль визуальной новеллы
└── GCombat            # Модуль боевой системы
```

Каждый модуль имеет собственную область ответственности и внутреннее хранилище состояния. Это позволяет развивать игровые подсистемы независимо друг от друга, не перенося их специфическую логику в центральное ядро.

## Основные компоненты

### Core — центральное ядро

Расположено в `core/`. Скрипт `core.gd` координирует работу модулей и предоставляет общие механизмы, которые используются разными частями игры.

Основные обязанности:

- Создание и управление вспомогательными инструментами.
- Сбор данных игровых модулей при создании сохранения.
- Запись и чтение файлов сохранений в каталоге `user://`.
- Передача данных сохранения соответствующим модулям при загрузке.
- Запоминание сцены, из которой было создано сохранение.
- Обработка общих ошибок и вывод отладочной информации.

Вспомогательные узлы создаются через `ToolFactory` из скриптов. Фабрика загружает скрипт, создаёт экземпляр, задаёт ему имя и добавляет его к родительскому узлу.

#### Инструменты ядра

Каталог `core/tools/` содержит переиспользуемые инструменты:

| Файл | Назначение |
| --- | --- |
| `tool_factory.gd` | Создание вспомогательных узлов из скриптов |
| `tools.gd` | Общие утилиты: чтение строк, версия проекта, вероятностные проверки |
| `scene_tools.gd` | Получение пути текущей сцены, переход и перезапуск сцены |
| `time_tools.gd` | Получение системной даты и времени |
| `window_tools.gd` | Операции с окном и получение скриншота |
| `platform_tools.gd` | Определение платформы и типа устройства |

В `core/classes/` находятся общие классы и компоненты, в том числе элементы интерфейса и работы со звуком. Каталог `core/py/` содержит Python-скрипты, вызываемые через PythonBridge.

### GVisualNovel — модуль визуальной новеллы

Расположен в `godo_visual_novel/`. Отвечает за механику визуальной новеллы и её состояние.

Основные части:

- `core/visual_novel.gd` — управляющий узел модуля. Предоставляет интерфейс для работы с данными новеллы, языком, именами персонажей, эмоциями, настройками текста и закладками.
- `core/classes/` — классы, реализующие элементы новеллы: чат, линейный диалог, реплики, персонажей, фон, музыку, звуки и действия.
- `data/gvn_data.gd` — данные модуля: цвета персонажей, языковые таблицы имён и эмоций, настройки отображения и параметры текста.

Текущее состояние модуля хранится во внутреннем буфере. Методы `get_save()` и `load_save()` формируют данные для сохранения и восстанавливают их.

### GminiGame — модуль мини-игр

Расположен в `godo_mini_game/`. Изолирует состояние и логику мини-игр от остальных подсистем.

Основные части:

- `core/mini_game.gd` — управляющий узел модуля и хранилище его состояния.
- `core/classes/` — общие классы взаимодействия для мини-игр: действия, обработка нажатий, перетаскивание и поведение интерактивных областей.
- `tools/` — сцены и графические ресурсы, используемые мини-играми.

Состояние модуля хранится в словаре-буфере. При сохранении создаётся его копия, а при загрузке данные восстанавливаются из переданного словаря.

### GCombat — модуль боевой системы

Расположен в `godo_combat/`. Отвечает за игровые сущности, предметы, оружие, способности и состояние игрока.

Основные части:

- `core/gcombat.gd` — управляющий узел модуля. Предоставляет операции с инвентарём, оружием, экипировкой, предметами и способностями, а также сбор и восстановление состояния.
- `core/classes/` — классы боевой системы: сущности, предметы, оружие, способности, эффекты и боевые механики.
- `data/gc_data.gd` — хранилище справочных данных о предметах, оружии, способностях и уровнях.
- `scenes/` и `data/` — сцены и вспомогательные ресурсы интерфейса боевой системы.

Состояние игрока и боевой системы собирается в словарь сохранения отдельно от данных других модулей.

### Data — общие данные

Синглтон `Data` подключён через Autoload и предназначен для общих данных проекта, доступных из разных подсистем. Это отдельная точка хранения, не привязанная к внутренним буферам конкретного игрового модуля.

## Сохранения и загрузка

За общий процесс сохранения отвечает `Core`. Каждый игровой модуль самостоятельно знает, какие именно данные ему необходимо сохранить и как их восстановить. Ядро не должно разбирать внутреннюю структуру модульных данных — оно только собирает и распределяет их.

### Создание сохранения

1. `Core` запрашивает данные у `GCombat`, `GminiGame` и `GVisualNovel` через их методы `get_save()`.
2. Дополнительно сохраняются путь текущей сцены, версия проекта, дата и время, а также скриншот для иконки сохранения.
3. Все данные объединяются в один словарь.
4. Словарь записывается в файл с помощью `FileAccess.store_var()` в каталоге `user://`.

### Загрузка сохранения

1. `Core` читает файл и проверяет, что в нём находятся корректные данные.
2. Данные соответствующих подсистем передаются в `load_save()` модулей.
3. После восстановления состояния ядро переключает игру на сохранённую сцену.

Таким образом, ответственность разделена: **модуль управляет собственными данными, ядро управляет общим процессом сохранения и загрузки**.

## PythonBridge

В проект подключён аддон PythonBridge. Он позволяет вызывать Python-функции из GDScript. Сейчас Python используется, в частности, для форматированного вывода структур данных сохранения в консоль.

Python-скрипты проекта находятся в `core/py/`. Путь к каталогу скриптов задаётся в настройках проекта.

## Структура каталогов

| Каталог / файл | Назначение |
| --- | --- |
| `addons/` | Подключённые плагины Godot, включая PythonBridge и Path Notes |
| `assets/` | Игровые ресурсы: изображения, звуки, модели и другие материалы |
| `core/` | Центральное ядро, общие классы, инструменты и Python-скрипты |
| `godo_combat/` | Модуль боевой системы |
| `godo_mini_game/` | Модуль мини-игр |
| `godo_visual_novel/` | Модуль визуальной новеллы |
| `scenes/` | Основные сцены проекта и связанные с ними скрипты |
| `entry_point.tscn` | Стартовая сцена проекта |
| `project.godot` | Конфигурация Godot, настройки проекта и список Autoload-синглтонов |

## Принципы расширения архитектуры

При добавлении новой функциональности рекомендуется придерживаться существующего разделения ответственности:

1. **Не переносить логику конкретной подсистемы в Core.** Ядро должно оставаться координатором, а не местом хранения всей игровой логики.
2. **Хранить состояние внутри соответствующего модуля.** Другие подсистемы должны обращаться к нему через публичные методы, а не изменять внутренние структуры напрямую.
3. **Соблюдать единый интерфейс сохранения.** Если модулю требуется сохранять состояние, он должен предоставлять методы `get_save()` и `load_save()`.
4. **Выносить повторно используемые операции в инструменты или общие классы.** Это позволяет не дублировать код между модулями.
5. **Использовать ToolFactory для создания вспомогательных узлов из скриптов**, когда это соответствует назначению компонента.

Такая структура позволяет использовать отдельные игровые подсистемы как самостоятельные модули и постепенно расширять проект без концентрации всей логики в одном скрипте.
